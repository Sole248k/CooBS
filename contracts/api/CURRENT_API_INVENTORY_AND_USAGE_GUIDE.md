# 1. Global Routing & Gateway Architecture

All external client traffic (Web Browser, Mobile PWA, Staff Terminals, External Capstone Banks) connects strictly through **Spring Cloud Gateway** (`api-gateway` on Port **8080**). Microservices on ports `8081` through `8085` reside in a private Docker bridge network (`core-banking-net`).

```
                    [Client Channels / Frontend :5173]
                                   │
                                   ▼
             ┌───────────────────────────────────────────┐
             │         API Gateway (Port 8080)           │
             │   Redis Token-Bucket Rate Limiter & CORS  │
             └─────────────────────┬─────────────────────┘
                                   │
         ┌─────────────────────────┼─────────────────────────┐
         │ /api/v1/auth/**         │ /api/v1/accounts/**     │ /api/v1/ledger/**
         ▼                         │ /api/v1/customers/**    ▼
   auth-service                    ▼                    ledger-service
    (Port 8081)             account-service              (Port 8083)
                             (Port 8082)                     │
                                   │                         ▼
         ┌─────────────────────────┼─────────────────────────┤
         │ /api/v1/notifications/**│ /api/v1/audit/**        │ Kafka Events
         ▼                         ▼                         ▼
notification-service         audit-service            Kafka Broker
    (Port 8084)               (Port 8085)             (Port 9092)
```

# 2. Global Standard Request & Response Headers

| Header | Format / Example | Required For | Purpose & Handling |
| :--- | :--- | :---: | :--- |
| `Authorization` | `Bearer eyJhbGciOi...` | All Secured APIs | JWT token containing user identity, customer ID, and roles (`ROLE_CUSTOMER`, `ROLE_TELLER`, `ROLE_ADMIN`). Validated statelessly. |
| `X-Correlation-ID`| UUIDv4 (`e7b8c1...`) | Every Request | Injected by API Gateway if missing. Propagated through all downstream HTTP and Kafka calls for distributed tracing. |
| `Idempotency-Key`| UUIDv4 (`f81d4f...`) | `/api/v1/ledger/**` | Generated by client before calling financial mutations. Checked in Redis via `SETNX` (60s lock) to prevent double debits/credits. |
| `Content-Type` | `application/json` | All `POST`/`PUT`/`PATCH` | UTF-8 JSON payload format. |
| `Accept` | `application/json` | All Requests | Content negotiation; error formats follow RFC 7807 `application/problem+json`. |

## 3.1 Auth Service (`auth-service` :8081)

The Auth Service manages credentials, JWT lifecycle, TOTP MFA, and Redis token blacklists.

### 1. `POST /api/v1/auth/customers/register`
* **What it is:** Public self-service registration endpoint for new cooperative members.
* **How it is used:**
  * **Caller:** Frontend `RegisterModal` / onboarding flow.
  * **Request Body (`CustomerRegistrationDto`):**
    ```json
    {
      "username": "maria.santos",
      "password": "Password123!",
      "email": "maria.santos@example.com",
      "firstName": "Maria",
      "lastName": "Santos",
      "phone": "+639175550123"
    }
    ```
  * **Processing:** Hashes password with BCrypt (strength 12), persists user in Oracle `USERS` table with role `ROLE_CUSTOMER`, generates initial JWT access token + refresh token.
  * **Response (`201 CREATED` - `AuthResponseDto`):**
    ```json
    {
      "accessToken": "eyJhbGciOiJIUzM4N...",
      "refreshToken": "7c9e6679-7425-40de...",
      "tokenType": "Bearer",
      "expiresIn": 900,
      "customerId": 105,
      "username": "maria.santos",
      "roles": ["ROLE_CUSTOMER"]
    }
    ```

### 2. `POST /api/v1/auth/customers/login`
* **What it is:** Customer authentication entrypoint.
* **How it is used:**
  * **Caller:** Frontend `apiClient.loginCustomer()` in `frontend/src/services/api.ts` line 281.
  * **Request Body (`LoginRequestDto`):**
    ```json
    {
      "username": "john_doe",
      "password": "Password123!"
    }
    ```
  * **Processing:** Verifies BCrypt hash. If MFA is enabled, returns `mfaRequired: true` with a temporary `mfaSessionToken`. If MFA is disabled, issues full `AuthResponseDto`.
  * **Response (`200 OK` - `LoginResultDto`):**
    ```json
    {
      "mfaRequired": false,
      "authResponse": {
        "accessToken": "eyJhbGciOiJIUzM4...",
        "refreshToken": "9b1deb4d-3b7d-4bad...",
        "tokenType": "Bearer",
        "expiresIn": 900,
        "customerId": 1,
        "username": "john_doe",
        "roles": ["ROLE_CUSTOMER"]
      }
    }
    ```

### 3. `POST /api/v1/auth/customers/mfa/verify`
* **What it is:** Verifies a 6-digit TOTP code during customer 2-factor login.
* **How it is used:**
  * **Caller:** Frontend MFA prompt modal after receiving `mfaRequired: true`.
  * **Request Body (`MfaVerifyRequestDto`):**
    ```json
    {
      "username": "john_doe",
      "totpCode": "482910",
      "mfaSessionToken": "session_uuid..."
    }
    ```
  * **Response (`200 OK`):** Returns full `AuthResponseDto` containing active tokens.

### 4. `POST /api/v1/auth/staff/login`
* **What it is:** Internal bank staff (Tellers, Compliance Officers, Admins) authentication.
* **How it is used:**
  * **Caller:** Frontend `apiClient.loginStaff()` in `frontend/src/services/api.ts` line 321.
  * **Request Body:** Same `LoginRequestDto` (username/password).
  * **Processing:** Validates staff credentials and checks `STAFF_USER` table; returns `roles: ["ROLE_TELLER"]` or `["ROLE_ADMIN"]`.
  * **Response (`200 OK`):** Returns `LoginResultDto`.

### 5. `POST /api/v1/auth/staff/mfa/verify`
* **What it is:** Mandatory 2FA verification for internal bank employees.
* **How it is used:** Same as customer MFA, but issues staff-authorized JWT claims.

### 6. `POST /api/v1/auth/token/refresh`
* **What it is:** Silent access-token renewal.
* **How it is used:**
  * **Caller:** Frontend HTTP client interceptor when an API call returns `401 Unauthorized`.
  * **Request Body (`RefreshTokenRequestDto`):**
    ```json
    {
      "refreshToken": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d"
    }
    ```
  * **Response (`200 OK`):** Fresh `accessToken` with a new 15-minute expiration.

### 7. `POST /api/v1/auth/token/revoke`
* **What it is:** Secure logout and token session revocation.
* **How it is used:**
  * **Caller:** Frontend logout button.
  * **Headers:** `Authorization: Bearer <token>`
  * **Processing:** Extracts `jti` (JWT ID) and writes `blacklist:{jti}` to Redis with remaining TTL. Subsequent requests with this token are rejected at the gateway.
  * **Response (`204 NO CONTENT`).**

### 8. `GET /api/v1/auth/token/me`
* **What it is:** Returns active user profile, roles, and session metadata from the token.
* **How it is used:**
  * **Caller:** App initialization on page refresh to restore user context.
  * **Response (`200 OK` - `UserProfileDto`):**
    ```json
    {
      "userId": 1,
      "username": "john_doe",
      "email": "john.doe@example.com",
      "roles": ["ROLE_CUSTOMER"],
      "enabled": true
    }
    ```

## 3.3 Ledger Service (`ledger-service` :8083)

The Ledger Service is the **authoritative financial engine**. It performs atomic double-entry balance mutations, ordered pessimistic row-locking on Oracle XE 23ai, and synchronous dual-writes to the PostgreSQL audit store.

### 29. `GET /api/v1/ledger/accounts/{accountId}/balance`
* **What it is:** Sub-millisecond balance query with a 10-second Redis cache.
* **How it is used:**
  * **Caller:** High-frequency balance inquiries from frontend, gateway pre-flight checks, and ATM/mobile apps.
  * **Alias:** Also responds to `/api/v1/ledger/balance/{accountId}`.
  * **Processing:**
    1. Checks Redis key `ledger:balance:{accountId}`. If hit, returns immediately (`isCached: true`).
    2. On cache miss, queries Oracle XE `BALANCE` table, caches JSON in Redis (TTL 10s), and returns (`isCached: false`).
  * **Response (`200 OK` - `BalanceResponseDto`):**
    ```json
    {
      "accountId": 1,
      "currency": "PHP",
      "availableBalance": 14750.50,
      "asOfTimestamp": "2026-10-03T11:30:00Z",
      "isCached": true
    }
    ```

### 30. `POST /api/v1/ledger/debits`
* **What it is:** Executes a single-account debit (withdrawal, fee deduction, loan payment).
* **How it is used:**
  * **Caller:** Frontend `apiClient.withdrawCash()` line 1068, or internal batch fee jobs.
  * **Alias:** Also responds to `/api/v1/ledger/debit`.
  * **Headers:** `Idempotency-Key: UUIDv4` (Mandatory).
  * **Request Body (`DebitCreditRequestDto`):**
    ```json
    {
      "accountId": 1,
      "amount": 500.00,
      "referenceNo": "WD-20261003-001",
      "remarks": "ATM Cash Withdrawal",
      "channel": "ATM"
    }
    ```
  * **Processing:**
    1. Acquires pessimistic lock: `SELECT ... FOR UPDATE` on account balance row.
    2. Verifies Oracle check constraint: `balance - amount >= 0`. Throws `InsufficientFundsException` if negative.
    3. Mutates Oracle `BALANCE` and inserts Oracle `TRANSACTION` row.
    4. Writes synchronous record to PostgreSQL `audit_store`. If audit write fails, rolls back Oracle transaction.
    5. Invalidates Redis balance cache.
  * **Response (`201 CREATED` - `DebitCreditResponseDto`):**
    ```json
    {
      "transactionId": 5001,
      "accountId": 1,
      "type": "DEBIT",
      "amount": 500.00,
      "remainingBalance": 14250.50,
      "referenceNo": "WD-20261003-001",
      "timestamp": "2026-10-03T11:35:00Z"
    }
    ```

### 31. `POST /api/v1/ledger/credits`
* **What it is:** Executes a single-account credit (cash deposit, payroll credit, interest payout).
* **How it is used:**
  * **Caller:** Frontend `apiClient.depositCash()` line 1042, or EOD interest runner.
  * **Alias:** Also responds to `/api/v1/ledger/credit`.
  * **Headers:** `Idempotency-Key: UUIDv4` (Mandatory).
  * **Request Body:** Same `DebitCreditRequestDto`.
  * **Response (`201 CREATED` - `DebitCreditResponseDto`):** Type `CREDIT`, balance incremented.

### 32. `POST /api/v1/ledger/transfers`
* **What it is:** The **mission-critical atomic double-entry fund transfer** between two accounts.
* **How it is used:**
  * **Caller:** Frontend `apiClient.executeTransfer()` line 912, or the future `orchestration-service`.
  * **Alias:** Also responds to `/api/v1/ledger/transfer`.
  * **Headers:** `Idempotency-Key: UUIDv4` (Strictly enforced).
  * **Request Body (`TransferRequestDto`):**
    ```json
    {
      "sourceAccountId": 1,
      "destinationAccountId": 2,
      "amount": 2500.00,
      "referenceNo": "TX-20261003-8821",
      "remarks": "P2P Coop Transfer"
    }
    ```
  * **Processing (Strict Double-Entry Accounting):**
    1. **Idempotency Guard:** Redis `SETNX idempotency:{key}` prevents concurrent duplicate requests.
    2. **Deadlock-Free Row Locking:** Orders account IDs deterministically:
       $$\text{Lock } \min(\text{src}, \text{dst}) \implies \text{Lock } \max(\text{src}, \text{dst})$$
    3. **Balance Validation:** Verifies sender has sufficient available funds.
    4. **Atomic Oracle XE Mutation:** Deducts sender balance, increments recipient balance, inserts two balanced `TRANSACTION` rows.
    5. **PostgreSQL Dual-Write:** Synchronously writes matching audit records triggering PostgreSQL SHA-256 hash chaining.
    6. **Event Emitted:** Publishes `ledger.transfer.completed.v1` event to Kafka broker (`topic: ledger.transfer.completed.v1`).
    7. **Cache Evicted:** Deletes Redis cached balances for both accounts.
  * **Response (`201 CREATED` - `TransferResponseDto`):**
    ```json
    {
      "transferReference": "TX-20261003-8821",
      "status": "SUCCESS",
      "sourceAccountId": 1,
      "destinationAccountId": 2,
      "amount": 2500.00,
      "timestamp": "2026-10-03T11:40:00Z"
    }
    ```

## 3.5 Audit Service (`audit-service` :8085)

The Audit Service provides read-only forensic queries and cryptographic verification of the PostgreSQL append-only hash chain.

### 36. `GET /api/v1/audit/accounts/{accountId}/statement`
* **What it is:** Cryptographic account statement showing balance progression and hash signatures.
* **How it is used:**
  * **Caller:** Frontend `apiClient.getAccountAuditStatements()` line 1101.
  * **Security:** `hasAnyRole('CUSTOMER', 'TELLER', 'ADMIN')`.

### 37. `GET /api/v1/audit/transactions/{transactionId}`
* **What it is:** Deep forensic audit record for a single transaction.
* **How it is used:** Compliance audit screen; displays IP address, actor ID, and exact dual-write timestamps.
* **Response (`200 OK` - `ForensicAuditResponseDto`).**

### 38. `GET /api/v1/audit/verify-chain/{accountId}`
* **What it is:** **Cryptographic Tamper-Proof Audit Chain Verification.**
* **How it is used:**
  * **Caller:** Frontend `apiClient.verifyChainIntegrity()` line 1133.
  * **Security:** `hasAnyRole('CUSTOMER', 'TELLER', 'ADMIN', 'AUDITOR')`.
  * **Processing:** Traverses every sequential row in PostgreSQL `audit_store` for the account, recalculates the SHA-256 hash using:
    $$\text{Hash}_n = \text{SHA256}(\text{id} \mathbin{\Vert} \text{account} \mathbin{\Vert} \text{amount} \mathbin{\Vert} \text{type} \mathbin{\Vert} \text{timestamp} \mathbin{\Vert} \text{Hash}_{n-1})$$
    and compares it against the recorded hash.
  * **Response (`200 OK` - `ChainVerificationResponseDto`):**
    ```json
    {
      "accountId": 1,
      "totalEntries": 42,
      "verifiedEntries": 42,
      "isChainIntact": true,
      "brokenAtAuditId": null,
      "computedHash": "a3f5b8e9c1...",
      "recordedHash": "a3f5b8e9c1..."
    }
    ```
